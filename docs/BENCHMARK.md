# 벤치마크

RTX 3090 24GB · Windows 11 · Python 3.12.10 · torch 2.10.0+cu130 · upstream `cdbb2bb`

측정값은 이 워크스테이션 기준이다. 데스크톱이 GPU 를 2~3GB 점유한 상태에서 잰 것이라
GPU 를 비우면 조금 더 나온다.

### 저장소 동봉 샘플 5장 (1024 · 웹 · 한 세션 연속)

저장소에 실제로 들어있는 5장을 한 번에 돌린 값이다. 총 24.7분.
(`inputs/samples/` 에는 upstream 샘플 13장이 있지만 커밋된 것은 5장이다.)

    inputs\samples\9_img.png inputs\samples\21_img.png inputs\samples\s_18_img.png

| 입력 | 소요 | 최대 VRAM | 원본 GLB | 경량 GLB | 정점 | 삼각형 |
|---|---:|---:|---:|---:|---:|---:|
| `1_img.png` | 221.3s | 14.22GB | 41.1MB | 10.0MB | 792,941 | 926,489 |
| `4_img.png` | 258.4s | 14.22GB | 36.3MB | 7.6MB | 709,077 | 949,617 |
| `9_img.png` | 556.5s | 14.23GB | 41.2MB | 9.1MB | 838,376 | 993,864 |
| `21_img.png` | 193.4s | 14.22GB | 38.8MB | 8.1MB | 761,924 | 997,202 |
| `s_18_img.png` | 247.2s | 14.22GB | 38.7MB | 7.8MB | 753,781 | 999,716 |

읽을 것이 두 가지 있다.

**VRAM 은 입력과 무관하게 일정하다** — 14.22~14.23GB, 편차 10MB. 해상도가
정하는 값이지 이미지가 정하는 값이 아니다. 용량 계획을 세울 때 이 점이 편하다.

**소요는 그렇지 않다** — 193초에서 556초까지 2.9배 벌어진다. 전부 GLB 추출의
`Parameterizing new mesh` 에서 갈린다(아래 참고). 5건을 연속으로 돌렸는데도
VRAM 이 흔들리지 않았으므로 파편화 누적은 이 규모에서 문제가 아니다.

### CLI 가 웹보다 느린 이유

모델 로딩 때문이다. CLI 는 매 실행마다 22GB 체크포인트를 다시 읽지만,
웹 서버는 프로세스에 상주시킨다. 순수 생성 시간은 양쪽이 같다.

이것이 계획서가 "요청마다 `inference.py` 를 새로 띄우지 않는다"를
아키텍처 제약으로 못 박은 이유다.

| 구간 | 시간 |
|---|---:|
| 모델 로딩 (서버 기동 시 1회) | 90~170s |
| 전처리 (배경 제거) | 0.0~0.6s |
| 카메라 추정 (MoGe) | 7~13s |
| 3단 캐스케이드 생성 | 100~150s (1024) · 210s (1536) |
| GLB 추출 2벌 | 20s ~ **7분** (아래 참고) |

모델 로딩 시간이 90초와 170초로 갈리는 것은 디스크 캐시 때문이다.
막 재부팅했거나 다른 작업이 페이지 캐시를 밀어낸 뒤에는 170초 쪽에 가깝다.

## 소요 시간의 편차는 GLB 추출에서 온다

1024 해상도 세 번의 소요가 178초 · 215초 · **742초**로 벌어졌다.
생성 구간은 거의 같았고, 전부 `Extracting GLB` 안에서 갈렸다.

| 하위 단계 | 빠른 경우 | 느린 경우 |
|---|---:|---:|
| Building BVH | 17s | 17s |
| Cleaning mesh | 32s | 112s |
| **Parameterizing new mesh** | **17s** | **229s** |
| Sampling attributes | 5s | 5s |
| Finalizing mesh | 25s | 25s |

`Parameterizing new mesh` 는 cumesh 의 UV 아틀라스 생성이다. CPU 에서 돌고,
메시 위상(topology)에 따라 비용이 크게 달라진다. 같은 입력이라도 생성 결과가
매번 조금씩 다르므로(아래 S6) 이 비용도 매번 달라진다.

**이 구간은 C 확장 안에서 GIL 을 오래 쥔다.** 그동안 웹 서버 응답이 밀려
진행률 폴링이 30초를 넘길 수 있다. 클라이언트가 이것을 실패로 접지 않도록
`tools/_api.py` 의 `poll()` 이 연속 실패 20회까지 견딘다.
(자세한 사고 경위는 `docs/TROUBLESHOOTING.md`)

## VRAM

| 항목 | 값 |
|---|---:|
| 총 VRAM | 24.0GB |
| 데스크톱 점유 (Edge, Slack 등) | 2.7~3.4GB |
| 생성 중 최대 — 1024 | **14.2GB** |
| 생성 중 최대 — 1536 | **18.7GB** |
| 1536 실행 시 남는 여유 | 약 2.6GB |

**1536 은 OOM 없이 통과했다.** 계획서 리스크 R4 는 24GB 에서 1536 을
"best-effort"로 낮춰 잡았는데, `low_vram` 을 켜둔 채라면 실제로는 돈다.

다만 여유가 2.6GB 뿐이므로 조건이 붙는다.

- 데스크톱 GPU 점유를 3GB 이하로 유지해야 한다. 브라우저에서 영상을 틀거나
  다른 GPU 앱을 열면 이 여유가 그대로 잠식된다.
- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 는 **Windows 에서 무시된다.**
  파편화 완화 수단이 하나 없으므로, 여러 건을 연달아 돌릴 때는 1024 가 안전하다.
- 1536 을 쓰려면 `.env` 에 `DEFAULT_RESOLUTION=1536` 을 두거나
  웹 UI 의 해상도 선택에서 고른다.

1536 은 시간을 2.3배 쓰고 정점 수를 1.22배 얻는다 (795,792 → 972,398).
`full.glb` 의 폴리곤 목표가 100만이므로 1536 은 그 상한에 거의 닿는다.

## 재현성 (S6)

**같은 seed 로 돌려도 결과가 매번 다르다.** 같은 이미지·seed 42·1024 로 3회:

| 실행 | 정점 | 삼각형 | `full.glb` SHA-256 앞 24자리 |
|---|---:|---:|---|
| 1 | 792,017 | 927,087 | `e01a380efd54362a28bdd09b` |
| 2 | 797,445 | 926,372 | `71efc222eff4e1238c9a1395` |
| 3 | 795,792 | 926,135 | `4ea9c1873f6394482d220b18` |

편차는 정점 기준 0.68%, 삼각형 기준 0.10% 다.

원인은 생성 단계에 있다. **`processed.png` 는 네 번 모두 비트 단위로 동일했다**
(`63ef013a59ed50b4...`). 배경 제거는 결정적이고 따라서 생성에 들어가는 입력이
같은데 출력이 갈린다. 남는 후보는 CUDA 커널 쪽 — cuDNN 알고리즘 자동선택,
TF32, 희소 복셀 커널의 atomic 누적 순서다.

### `DETERMINISTIC=1` 은 듣지 않는다

cuDNN 알고리즘 자동선택과 TF32 를 끄고 같은 조건으로 2회 돌렸다.

| 모드 | 소요 | 정점 | 삼각형 |
|---|---:|---:|---:|
| 기본 | 178.5s / 215.3s / 742.5s | 792,017 / 795,792 / 797,445 | 926,135 ~ 927,087 |
| `DETERMINISTIC=1` | 346.5s / 370.5s | 797,546 / 815,286 | 943,492 / 962,776 |

**재현되지 않는다.** 바이트는 물론 정점 수도 갈렸다. 오히려 편차가
0.68% 에서 2.2% 로 커졌고(측정 2회뿐이라 이 수치 자체는 흔들릴 수 있다),
소요는 70% 늘었다.

결론은 분명하다 — 남은 비결정성의 주된 원인은 cuDNN 도 TF32 도 아니다.
희소 복셀 커널의 atomic 누적 순서 쪽이 유력하고, 그것은 이 스위치로
통제되지 않는다. **기본값 0 을 유지한다.** 스위치를 지우지 않고 남겨 둔 것은
"이건 이미 해봤고 안 된다"를 코드와 문서에 남기기 위해서다.

### S6 판정

**미달성.** 바이트 단위 재현도, 정점 수 일치도 얻지 못했다.

실용적으로는 이렇게 다룬다.

- 결과 비교는 파일 해시가 아니라 **정점·삼각형 수와 육안**으로 한다.
- 기본 모드의 0.7% 편차는 형상이 바뀌는 수준이 아니다. "같은 입력에
  같은 물건이 나온다"는 느슨한 의미의 재현성은 성립한다.
- 정확한 재현이 필요하면 GLB 를 보관한다. 다시 만들어서 같은 것을
  얻을 수는 없다.

## 측정 방법

```powershell
# 웹 서버 (별도 창) — 모델 상주
powershell -File setup\run_server.ps1

# 한 건 종단 검증
python tools\e2e_test.py

# 배치 — 여러 장, 또는 같은 장을 여러 번
python tools\run_batch.py                                   # inputs\samples 전부
python tools\run_batch.py inputs\samples\1_img.png --resolution 1536
python tools\run_batch.py inputs\samples\1_img.png --repeat 3   # 재현성

# CLI 단독 (모델을 매번 로드한다)
powershell -File setup\06_smoke_inference.ps1 -Resolution 1024
```

`run_batch.py` 는 `reports/batch_<타임스탬프>.md` 에 같은 표를 남긴다.

`peak_vram_gb` 는 `torch.cuda.max_memory_allocated()` 로 생성 구간만 잰다.
`vertices` / `triangles` 는 최종 GLB 의 accessor count 를 직접 읽는다 —
파이프라인이 보고한 값이 아니라 파일에서 센다.

각 실행의 `runs/<id>/meta.json` 에 같은 값이 남는다.

## 클린 설치 (S7)

`setup/verify_clean_install.ps1` — 별도 venv 에 01→04 를 그대로 태운다.

| 항목 | 값 |
|---|---:|
| 소요 | **7.5분** |
| 재사용 | `models/` (가중치 24.7GB) · `upstream/` · `cache/pip` |
| 판정 | G2 통과 · `MoGeModel` import 확인 |

가중치 다운로드와 upstream 클론은 포함하지 않는다. 둘 다 "있으면 건너뛴다"로
짜여 있어 여기서 다시 받지 않는다. 맨바닥에서 재는 값이 필요하면
`models/` 와 `upstream/` 까지 지워야 하고, 그건 25GB 재다운로드다.

이 검증이 설치 스크립트 결함 6건을 찾아냈다. 자세한 내용은
`docs/TROUBLESHOOTING.md` 와 `PLAN.md` 를 참고한다.
